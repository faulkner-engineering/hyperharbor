# HyperHarbor security baseline, 2026-10-06

Status: first baseline review. Static code review only. Nothing was built, run, or tested, and the review ran on
Linux, so all Windows behavior (ACLs, DPAPI, SChannel, Hyper-V, service and scheduled-task behavior) is inferred
from code. Findings marked "needs Windows verification" must be confirmed on a real host before they are ranked
final.

Branch reviewed: `claude/claude-code-web-bzduqy` (default branch contents at session start).

## 1. Executive summary

HyperHarbor's core security design is sound. The pairing protocol (SPAKE2 with certificate-bound transcript),
certificate pinning, per-request device authentication, the elevation model, secret handling for VM
credentials, and untrusted-input parsing are well built and, in most places, covered by tests that enforce the
invariants in CLAUDE.md. No Critical findings were identified.

The weaknesses cluster in four places:

1. **The update trust root.** Updates are verified only by a SHA-256 that comes from the same GitHub release as
   the package. The signing hook accepts everything, auto-update is on by default, and the downloaded executable
   runs as SYSTEM during the self-test before any install decision. A compromise of the release channel is a
   compromise of every auto-updating host.
2. **The tray named pipe.** Any process running as the tray user can use the pipe to read pairing PINs and set
   the admin passphrase without knowing the old one, which unlocks every elevated action.
3. **Unauthenticated, unthrottled endpoints.** Anonymous pairing has no rate limit. The same gap lets a LAN
   attacker block pairing, defer self-updates, and push real events out of the capped audit log.
4. **Release pipeline hardening.** Actions are pinned by tag, the whole workflow holds `contents: write`, and the
   tag name is interpolated into PowerShell.

Counts: 2 High, 10 Medium (one of them a standing verification item), 25 Low, 9 Info, after merging duplicate
findings from the five review tracks.

## 3. What works well

Controls verified by reading the code. File references are to the reviewed revision.

- **Pairing.** SPAKE2 matches `docs/pairing.md` in both C# and Rust (shared vectors). Received shares are
  validated against the subgroup. The transcript binds both certificate hashes, so a relay with a different
  certificate fails. The PIN is 6 digits from a CSPRNG, expires in 120 s, allows 5 attempts, and is never logged.
  Comparisons are constant-time. Replay is blocked by a random pairing id and by destroying the request.
- **Authentication.** The client certificate fingerprint is checked against the paired store on every request
  (`PairedDeviceAuthenticationHandler.cs`). The fallback policy requires an authenticated device and only the
  three pairing routes are anonymous. `EndpointSecurityTests` enforce route and contract parity, that every
  non-GET route is audited, and that elevated routes are audited. The test-only certificate header exists only in
  the test project.
- **Client pinning.** SHA-256 pinning with handshake signature verification still enforced (`tls.rs`). Tokens
  and credentials are never sent before the pin check. Retries happen only on connection errors.
- **Elevation.** 32-byte random tokens, stored as SHA-256, constant-time compared, bound to device and User,
  short-lived, revoked on unpair or passphrase change. PBKDF2-SHA256 at 600,000 iterations. The plaintext
  passphrase never crosses the pipe.
- **Audit.** A "requested" entry is written before the handler and fails closed (503). Detail text is stripped of
  control characters and capped.
- **Secrets.** Guest scripts travel as `-EncodedCommand` with credentials on stdin only. SSH passes secrets on
  stdin. Secret-bearing types hide values in `ToString` and `Debug`. Client credential handling uses
  session-scoped tagged Credential Manager entries, zeroized, and removed after launch.
- **Injection resistance.** No script, XML, or YAML injection found. Guest arguments are JSON values or arrays,
  XML is built with `XElement`, cloud-init scalars are quoted, and profile ids and account names are
  regex-validated before any use.
- **Console.** The tunnel target is fixed in configuration. Tickets are 256-bit, hashed, bound to device, User,
  and VM, and expire after 120 s. The console account is a hardened standard user with logon rights denied.
- **SSH.** Host key pinning with an explicit `trustNewHostKey` opt-in.
- **Client web surface.** Strict CSP, no `{@html}`, no shell, fs, or opener plugin, the elevation token never
  reaches JavaScript, and `.rdp` input is strictly validated.
- **Parsing.** YAML profiles are read through the representation model with unknown keys rejected and size
  caps. Outbound fetches use fixed hosts with the allowlist re-checked per redirect hop and decompressed body
  caps. The update downloader enforces https, host allowlist per hop, size, and streamed SHA-256.
- **Update mechanics.** Crash-safe state machine, rollback with data restore, anti-downgrade, strict SemVer,
  health check that needs a live process plus a pinned TLS handshake, and an update helper kept outside
  `versions\`.
- **Files.** ProtectedFile (atomic writes, protected ACLs, DPAPI), `DataDirectoryAcl`, ISO name validation with
  traversal tests, reparse points refused, `.partial` upload files.

### HH-SEC-01 High: unsigned self-update with auto-update on by default

- Where: `Host.Core/Updates/PackageSignatures.cs` (`UnsignedPackageVerifier`, "SIGNING HOOK (Phase 11,
  deferred)"), `UpdateOptions.cs` (`Mode = UpdateMode.Auto`), `UpdateManifest.cs`, `UpdatePreparer.cs`.
- Evidence: the verifier is a stub that accepts every package. The manifest, the package URL, and the hash all
  come from one GitHub release. The allowlist is by host (`github.com` and the asset hosts), so a manifest may
  point at any repository's release asset.
- Scenario: someone who can publish a release or replace `latest.json` (stolen token, compromised workflow,
  maintainer account takeover) gets an executable installed as the LocalSystem service on every auto-updating
  host. The host manages Hyper-V and holds guest administrator credentials, so this is full compromise of the
  host and its VMs.
- Fix, in order:
  1. Until signing exists, default `Mode` to `Notify` and mark Auto as unavailable.
  2. Verify a detached signature over `latest.json` with a public key embedded in the host (minisign or Ed25519),
     before any download. Make the verifier fail closed.
  3. Add Authenticode verification with a pinned signer (WinVerifyTrust plus thumbprint) and, optionally,
     Sigstore or GitHub artifact attestation bound to the release workflow identity.
  4. Require package URLs to start with
     `https://github.com/faulkner-engineering/hyperharbor/releases/download/`. Check redirect targets by host only.
  5. Add a signed timestamp or expiry to the manifest to detect freeze attacks (HH-SEC-43).
- References: CWE-494, CWE-345, CWE-347; SLSA build levels; The Update Framework; OWASP Top 10 2021 A08.

### HH-SEC-02 High: tray pipe lets any tray-user process set the admin passphrase

- Where: `Host.Service/Tray/TrayPipeServer.cs` (`CreatePipeSecurity`, `SetAdminPassphrase`, folder and update
  messages).
- Evidence (confirmed by reading): the installed service grants the tray user SID `ReadWrite | Synchronize` on
  the pipe. The server never authenticates the caller beyond that ACL. `SetAdminPassphrase` accepts a new hash
  with no check of the current passphrase. Other messages broadcast pairing PINs, set the ISO, VM, and backup
  folders, install updates, and unpair devices.
- Scenario: malware or a browser exploit running at the signed-in user's integrity level connects to the pipe,
  reads a pairing PIN, pairs its own device, sets a passphrase it knows, elevates, and then deletes VMs, uploads
  ISOs, or installs updates, all executed by the LocalSystem service with no UAC prompt. This is a path from a
  standard-user process to LocalSystem-driven actions.
- Note: CLAUDE.md documents the tray as the trust anchor for the passphrase, so some of this is accepted design.
  The unauthenticated passphrase takeover is the sharp edge.
- Fix:
  1. Require the current passphrase to change the passphrase. For first set, require a UAC prompt or Windows
     Hello on the tray side.
  2. Verify the pipe client with `GetNamedPipeClientProcessId`: image path under the install directory, signed
     once signing exists.
  3. Show the PIN only in an interactive tray window and require the user to accept a request before the PIN is
     generated.
  4. Record the caller SID and PID in tray audit entries (HH-SEC-15).
- References: CWE-284, CWE-306, CWE-250; OWASP Top 10 2021 A01; Microsoft: Named Pipe Security and Access Rights.

### HH-SEC-03 Medium: anonymous pairing has no rate limit

- Where: `PairingEndpoints.cs`, `PairingService.cs:65-116`, `AuditLog.cs:119-127`,
  `AuditEndpointFilter.cs`, `Program.cs` (no Kestrel limits).
- Evidence: `POST /pairing/requests` is anonymous with no throttle. Each request creates a PIN, notifies the
  tray, and writes audit entries. Audit rollover overwrites `audit.1.log` at 10 MB, so retention is about 20 MB.
  A pending pairing request counts as host activity, which the update gate treats as busy. SPAKE2 math (several
  3072-bit `ModPow` calls) runs under a global lock on unauthenticated input.
- Scenarios (code-path reasoning, not run):
  1. One request every 120 s holds the single pending slot, so real pairing returns 409.
  2. A request loop causes constant PIN windows and balloons (phishing and nuisance), and defers self-updates
     indefinitely.
  3. Thousands of cheap anonymous requests push earlier real audit events out of the retained files.
  4. A single LAN client can load a CPU core through unauthenticated big-integer exponentiation. Timings were not
     measured.
  5. PIN guessing is not practical: 5 attempts per request against 10^6, with a new PIN per request.
- Fix:
  1. Add the ASP.NET Core rate limiter (global and per-IP token bucket, for example 3 per minute) on the
     pairing routes, with a cooldown after abandoned or failed requests.
  2. Require the user to accept the request in the tray before the PIN is shown.
  3. Archive audit files (timestamped, size or age capped) instead of overwriting. Do not write one audit row
     per anonymous request, or keep them in a separate capped file.
  4. Do the SPAKE2 math outside the global lock and count invalid shares toward a budget.
  5. Set `MaxRequestBodySize` per route (about 64 KB for JSON) and connection limits (HH-SEC-17).
- References: CWE-770, CWE-307, CWE-779; OWASP API Security Top 10 2023 API4; Microsoft: Rate limiting
  middleware in ASP.NET Core.

### HH-SEC-04 Medium: downloaded package runs as SYSTEM before any install decision

- Where: `SelfTestGate.cs`, `UpdatePreparer.cs`.
- Evidence: after download and the (stub) signature step, the prepare phase copies the data directory with
  `DataBackup.Copy` and starts the downloaded executable with the service's token to run `--self-test`. The copy
  includes DPAPI machine-scope files (certificate key, guest credentials, console accounts, the admin passphrase
  hash).
- Scenario: a hash-matching malicious executable runs as SYSTEM at prepare time, even if the owner never installs
  the update.
- Fix: verify signatures first (HH-SEC-01). Run the self-test under a restricted token or job object, or a
  dedicated low-privilege account, against a scrubbed data copy (no credential stores, no certificate key). Clean
  up `update\selftest` after a crash as well as on the normal path.
- References: CWE-250, CWE-829.

### HH-SEC-05 Medium: release workflow hardening gaps

- Where: `.github/workflows/release.yml`.
- Evidence (confirmed by reading): `permissions: contents: write` applies to the whole workflow, including the
  build and test steps. Actions are pinned by tag (`actions/checkout@v4`, `dtolnay/rust-toolchain@stable`, a
  moving branch, and `Swatinem/rust-cache@v2`). `actions/checkout` keeps its token in `.git/config`.
  `'${{ github.ref_name }}'` is interpolated directly into PowerShell at lines 41, 61, and 63 (a tag name can
  contain quote and shell metacharacters), while lines 74 to 76 correctly use `env:`. There is no environment or
  required-reviewer gate, no build provenance, and no SBOM. Release builds restore caches written by CI runs.
  `npx --yes` in the client build runs unpinned packages in the release job.
- Fix:
  1. Pin every action to a full commit SHA and pin the Rust toolchain version.
  2. Split into a build job with `contents: read` and `persist-credentials: false`, and a small publish job
     behind a GitHub Environment with required reviewers.
  3. Pass `github.ref_name` through `env:` and validate it against a strict version regex.
  4. Add tag protection rules for `v*`.
  5. Disable caches for release builds.
  6. Add build provenance (`actions/attest-build-provenance`) and a CycloneDX SBOM, and add the signing step
     from HH-SEC-01 here.
  7. Check that `latest.json` for the beta channel only comes from this workflow.
- References: CWE-829, CWE-94; GitHub Docs: Security hardening for GitHub Actions; GitHub Security Lab: untrusted
  input in expressions; SLSA build levels; OpenSSF Scorecard (Pinned-Dependencies, Token-Permissions).
- Repository settings could not be verified (branch protection, Actions allowlist, default token permissions).

### HH-SEC-06 Medium: tray pipe can be squatted before the service starts

- Where: `TrayPipeServer.cs` (pipe creation, no `PipeOptions.FirstPipeInstance`), `TrayPipeClient.cs`.
- Correction to the track report: the pipe ACL does not grant the tray user create-instance rights
  (`TrayPipeServer.cs:508-530`), so the tray user cannot add instances to the service's pipe. The remaining risk
  is the one already in CLAUDE.md: before the service creates the pipe, any local process can create a pipe with
  that name and its own ACL. The service retries every 5 s without noticing, and the tray client connects to
  whichever server answers without verifying it.
- Scenario: a local process started before the service receives pairing PINs and the passphrase hash from the
  tray, and can send forged status messages to the tray.
- Fix: use `PipeOptions.FirstPipeInstance` on the first instance and fail loudly when it throws. In the client,
  verify the server with `GetNamedPipeServerProcessId` against the service process (image path and SID).
- References: CWE-300, CWE-362; Microsoft: `PipeOptions` and `FILE_FLAG_FIRST_PIPE_INSTANCE`.

### HH-SEC-07 Medium: disk export accepts any fully qualified path, including UNC

- Where: `Core/Lifecycle/VmDiskExportService.cs:99-103`.
- Evidence: the only check is `Path.IsPathFullyQualified`, so `\\host\share` passes. The tray folder setting has
  its own (also incomplete) UNC refusal, but the API field does not.
- Scenario: an elevated paired device exports VM disks to `\\attacker\share`. VM disks leave the host, and the
  machine account authenticates to the attacker over SMB (NTLM exposure).
- Fix: accept only the tray-configured backup folder, or require `DriveInfo.DriveType == DriveType.Fixed`.
  Reject UNC and device paths (`\\?\`, `\\.\`).
- References: CWE-22, CWE-73, CWE-918; Microsoft: path normalization in .NET.

### HH-SEC-08 Medium: ISO upload has no size cap

- Where: `Api/HostEndpoints.cs:84-93`, `IsoLibrary.cs:244-268`.
- Evidence: `MaxRequestBodySize = null`. The free-space check runs only when `Content-Length` is declared, so a
  chunked body skips it. Concurrent uploads are unlimited and the check is not atomic. Slow uploads hold the
  update gate open.
- Scenario: an elevated device fills the ISO volume, which disrupts the host if it is the system drive.
- Fix: enforce a configured maximum, require `Content-Length`, re-check free space during the copy with a
  reserve, and allow one upload at a time.
- References: CWE-400, CWE-770.

### HH-SEC-09 Medium: console relay and tunnel

- Where: `client/src-tauri/src/console.rs:117-190`, `Host.Service/Api/ConsoleEndpoints.cs`,
  `Host.Core/VmConsole/*`.
- Evidence and scenarios:
  1. The client loopback listener (`127.0.0.1:0`) accepts any local connection and tunnels it with the stored
     ticket until mstsc exits. On a shared client machine another local user can reach the host's VMMS console
     port, probe for VM existence, and attempt credential guessing. VMMS still authenticates, so this is not
     direct access.
  2. The ticket binds the URL's `vmId`, but the host copies opaque bytes and VMMS picks the VM from the client's
     pre-connection blob. A ticket for VM A can therefore reach VM B, subject to VMMS grants. Console grants are
     never revoked except by `--remove-console`, so the console account accumulates access to every VM it
     opened.
  3. There is no idle timeout or per-device tunnel cap, and tickets are multi-use for 120 s. Open tunnels
     survive ticket expiry and keep the host awake.
- Fix: accept one connection plus a short grace, or verify the peer PID or user; parse and verify the
  RDP_PRECONNECTION_PDU GUID equals the ticket's VM before pumping; revoke the grant when the last tunnel closes;
  cap and time out tunnels; close tunnels on unpair. Document that the console assumes a single-user client
  machine.
- References: CWE-923, CWE-306, CWE-639, CWE-400.
- Not verified: VMMS behavior for a mismatched blob, and whether VMMS grants are the only remaining control.

### HH-SEC-10 Medium: XML entity expansion when reading ISO metadata

- Where: `Host.Core/Unattend/IsoInspector.cs` (about line 110 to 118, `XDocument.Parse` on the WIM or ESD XML
  resource, up to 16 MB), and the `ReadAllBytes` read at about line 58.
- Evidence: no `XmlReaderSettings`. The default entity expansion limits for `XDocument.Parse` on .NET 8 were not
  verified by running it.
- Scenario: a crafted ISO (elevated upload, or a booby-trapped image the owner downloaded) makes the host
  allocate large amounts of memory when the image is inspected or used to create a VM, crashing the service.
- Fix: parse with `XmlReader.Create` and `DtdProcessing = Prohibit`, `XmlResolver = null`,
  `MaxCharactersFromEntities` set low. Bound the metadata read size. Add a test with a billion-laughs payload.
- References: CWE-776, CWE-400; OWASP XML External Entity Prevention Cheat Sheet.

### HH-SEC-11 Medium (needs Windows verification): single-file native extraction directory

- Where: `scripts/package.ps1` (`IncludeNativeLibrariesForSelfExtract=true`). Nothing sets
  `DOTNET_BUNDLE_EXTRACT_BASE_DIR`.
- Evidence: as LocalSystem, extraction defaults to a folder under `C:\Windows\Temp\.net\` whose name derives from
  the bundle id, which is predictable from the public executable. If a standard user can pre-create that
  directory (depends on the real ACL), planted native libraries load as SYSTEM.
- Fix: set the extraction base to an admin-only directory for the service and the update task, or avoid
  self-extraction. Verify on a Windows host first.
- References: CWE-427, CWE-426; Microsoft: single-file deployment overview.

### Low and Info findings (short form)

Each entry: where, risk, fix. References are listed in section 8.

- **HH-SEC-13 Backup and self-test copies leak briefly.** `DataBackup.CopyFile` copies and then applies the ACL,
  so a file inherits the directory ACL (which grants the tray user read) in the gap. Create the destination with
  the final security descriptor, or make `update\` SYSTEM and Administrators only. CWE-362, CWE-732.
- **HH-SEC-14 Global elevation lockout.** 20 failures per hour across all devices block everyone, and one paired
  device can trigger it repeatedly. Do not let an already-locked device consume the global budget, lock out per
  device and per IP, and add a passphrase strength check (minimum length is 8 today). CWE-307.
- **HH-SEC-15 Audit gaps and integrity.** `renameIso` omits the old name, profile updates and imports omit ids,
  tray actions record no caller SID or PID and fail open, and `Failed` entries record raw exception messages. The
  file has no hash chain. Log route values generically, add hash chaining and anchor to the Windows Event Log.
  CWE-778, CWE-345.
- **HH-SEC-16 Tray folder validation.** The UNC refusal is `StartsWith(@"\\")` on raw input, so `//server/share`
  passes after normalization. Mapped drives, folder ACLs, and hard links are not checked, and
  `IsoLibrary.List` deletes old `*.partial` files in the chosen folder. Normalize first, require a fixed drive,
  lock down the folder ACL. CWE-22, CWE-59.
- **HH-SEC-17 Kestrel limits.** Defaults apply (30 MB body even for anonymous routes), with no connection
  limits. Set per-route body limits and `MaxConcurrentConnections`. CWE-770.
- **HH-SEC-18 Unelevated state-changing or sensitive routes.** `startWakeTest` (sleeps the host), capture,
  `recordAppxBaseline`, and `cancelVmInstall` need no elevation. Decide whether they should. CWE-285.
- **HH-SEC-19 Rotated VM password lifetime.** The guest password stays valid until the next Connect, unlike the
  console password, which is re-rotated at the end of the window. Optionally re-rotate or document. CWE-613.
- **HH-SEC-20 Managed string copies.** Zeroing is partial because .NET strings are immutable. Accept and document,
  and narrow code comments that imply otherwise. CWE-316.
- **HH-SEC-21 First SSH provision trusts the guest-reported address.** On first provision or with
  `trustNewHostKey`, the admin password goes to whatever answers at that address. Show the fingerprint for user
  confirmation and limit keyboard-interactive to one prompt. CWE-300.
- **HH-SEC-22 One-time admin password after failure or cancel.** The seed ISO stays attached and on disk and the
  credential store keeps the password. Eject and delete the seed, and rotate or disable the one-time account on
  Failed and Canceled. Verify the Panther cached unattend and AutoLogon values in the guest. CWE-312, CWE-256.
- **HH-SEC-23 PowerShell by bare name.** `new ProcessStartInfo("powershell.exe")` as SYSTEM. Use the absolute
  `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`. CWE-426, CWE-427.
- **HH-SEC-24 DPAPI machine scope with static entropy.** Correct for a LocalSystem service, but protection rests on
  the ACL, and backups carry the blobs. Consider per-install random entropy in a separate protected file and
  document the threat model. CWE-522.
- **HH-SEC-25 `.rdp` temp file.** Predictable name in `%TEMP%`, written then launched non-atomically. Write into
  a per-run private directory with `create_new` and an unpredictable name. CWE-377, CWE-367.
- **HH-SEC-26 Install root.** `--root` accepts any path and uninstall deletes recursively without a sanity check
  (`--root C:\`). Require a root under `%ProgramFiles%`, refuse drive roots, and verify owner and ACL before the
  helper runs anything. CWE-276, CWE-732.
- **HH-SEC-27 Staged executable not re-verified.** Re-hash the staged executable and check its path prefix in the
  helper before `Stage()`. CWE-367.
- **HH-SEC-28 Elevation helper paths.** Uninstall copies the executable to the user's `%TEMP%` and then elevates
  that copy, and `--result-file` and `--setup-console` take caller-supplied paths that an elevated process
  writes. Use a per-user protected directory, `CreateNew`, no reparse following, and validate paths.
  CWE-377, CWE-59.
- **HH-SEC-29 Dependencies.** No NuGet lock files or Central Package Management, no `--locked` restores, unpinned
  `npx --yes` and `cargo install cargo-audit`, no Dependabot or Renovate, no CODEOWNERS, audits run in CI but
  not in the release workflow, and the package-search helper installs `Microsoft.WinGet.Client` from PSGallery
  without a version pin. CWE-1357.
- **HH-SEC-30 mDNS endpoint overwrite.** An unauthenticated announcement rewrites a paired host's stored
  addresses. Pinning blocks credential exposure, so this is DoS and redirection. Update stored endpoints only
  after a successful pinned connection. CWE-290.
- **HH-SEC-31 Device name spoofing.** Control characters are stripped but Unicode format characters (bidi
  overrides, zero-width) are not, and the prompt does not show the requester's IP. Strip Cf, Zl, Zp and show the
  source IP. CWE-451.
- **HH-SEC-32 Host key container.** `X509KeyStorageFlags.DefaultKeySet` may leave a CNG key container outside the
  DPAPI-protected PFX. Verify on Windows where the key lands and consider the documented ephemeral-key
  workaround. CWE-312.
- **HH-SEC-33 Tauri IPC scope.** About 55 commands are callable by any code in the webview. Mitigated by the CSP
  and no `{@html}`. Define an app manifest with per-command permissions and consider the isolation pattern.
  CWE-749.
- **HH-SEC-34 Unbounded caches.** `ExtensionResolver`, `PackageSearch`, and `IsoInspector` caches never evict.
  Use a size-capped cache and a per-device rate limit. CWE-770.
- **HH-SEC-35 Profile registry tweaks.** Imports can write any HKLM or HKCU value in a guest. Needs elevation and
  is audited. Show custom registry tweaks prominently in the import review. CWE-1357.
- **HH-SEC-36 RDP target IP.** The client uses the host-supplied address. Within the trust model (paired host).
  Optionally restrict to private ranges. CWE-940.
- **HH-SEC-37 Variable-time exponentiation.** Theoretical timing leak of the PIN-derived exponent. Document as
  accepted risk or move to an elliptic-curve SPAKE2. CWE-208.
- **HH-SEC-38 to HH-SEC-46 (Info).** Sanitize only redacts exact secret strings (sanitize inside the PowerShell
  runner where the credential is in scope); console rotation crash window; VMs shared across Users (record the
  decision before v2, OWASP API1); path text in job errors; TLS 1.2 and a 20-year certificate with no rotation or
  revocation path; no freeze-attack protection; path handling that is safe only because of check ordering and a
  backtracking regex without a timeout; client robustness notes; dev-only start script elevation.

## 5. Cross-cutting observations

1. **One missing limiter, three symptoms.** The lack of rate limiting on anonymous routes causes pairing
   lockout, deferred updates (pending pairing counts as activity), and audit eviction. A single limiter plus
   audit archiving closes all three (HH-SEC-03).
2. **The tray is the weakest trust boundary.** HH-SEC-02 and HH-SEC-06 together mean the passphrase, the PIN, and
   the update trigger all rest on a pipe whose callers are not authenticated. The "pipe squatting" open issue in
   CLAUDE.md understates this.
3. **The update path is the highest-value target.** HH-SEC-01, HH-SEC-04, HH-SEC-05, and HH-SEC-27 form one chain:
   unsigned artifacts, built by a loosely hardened workflow, executed as SYSTEM during prepare. Fix them together.
4. **Elevation is only as strong as the passphrase.** Brute force is bounded (about 480 guesses a day per host)
   but the minimum length is 8 with no strength check (HH-SEC-14).
5. **Same-user malware is mostly out of scope, and the design says so.** Several Low findings (`.rdp` file,
   Credential Manager window, loopback relay) assume an attacker already running as the user. They are worth
   cheap hardening but are not the priority.

## 6. Improvement roadmap

Order is by risk reduction per unit of effort. Each item names the findings it closes.

### Now (before the first public release)

1. Default `Update:Mode` to `Notify` until signing exists (HH-SEC-01).
2. Require the current passphrase to change the admin passphrase (HH-SEC-02).
3. Add `FirstPipeInstance` and a pipe-server check in the tray client (HH-SEC-06).
4. Rate-limit and accept-gate anonymous pairing, and archive audit logs instead of overwriting (HH-SEC-03).
5. Reject UNC and non-fixed paths for disk export and tray folders (HH-SEC-07, HH-SEC-16).
6. Parse ISO XML with a hardened reader (HH-SEC-10).
7. Pass `github.ref_name` through `env:`, scope token permissions, and pin actions by SHA (HH-SEC-05).
8. Set an upload size cap and require `Content-Length` (HH-SEC-08).

### Next

1. Implement manifest signing and Authenticode or Sigstore verification, with a fail-closed verifier and the
   repository URL prefix (HH-SEC-01, HH-SEC-04, HH-SEC-27).
2. Run the self-test under a restricted token on a scrubbed data copy (HH-SEC-04).
3. Split the release workflow into build and publish jobs behind an environment with required reviewers, and add
   provenance and an SBOM (HH-SEC-05).
4. Console hardening: parse and verify the connection blob, single-connection relay, tunnel caps, grant
   revocation (HH-SEC-09).
5. Verify on Windows: bundle extraction directory, host key container, `%ProgramFiles%` ACLs, update task
   security descriptor (HH-SEC-11, HH-SEC-32, HH-SEC-26).
6. Dependency hygiene: lock files, `--locked` restores, Dependabot, CODEOWNERS, audits in the release workflow
   (HH-SEC-29).

### Later

1. Audit hash chaining and Event Log forwarding (HH-SEC-15).
2. Scope Tauri commands with an app manifest (HH-SEC-33).
3. Decide the per-User ownership model for VMs before v2 (HH-SEC-40).
4. Host certificate rotation and a revocation story (HH-SEC-42).
5. Per-install DPAPI entropy and a documented threat model for backups (HH-SEC-24).

## 9. Using this baseline for pull request review

Check each pull request against these questions, which come from the invariants and the findings above:

1. Does every new non-GET route have `.Audited()`, and every destructive one `.RequireElevation()` and an
   `api.yaml` security entry? Is the audit summary free of secrets?
2. Does any new anonymous or unelevated route accept unbounded input, run expensive work, or write audit rows
   per request?
3. Do new paths, folders, or file names pass through the existing validators (ISO names, ids), and are UNC,
   device paths, and reparse points refused?
4. Do new guest scripts pass data as JSON or arrays, keep secrets on stdin, and sanitize errors?
5. Does any type holding a secret hide it in `ToString` and `Debug`, and is it zeroized where possible?
6. Does new XML, YAML, or archive parsing disable DTDs and external entities and cap sizes?
7. Do workflow changes pin actions by SHA, keep minimal permissions, and pass untrusted values through `env:`?
8. Do changes to the update, installer, or helper code keep fail-closed verification, protected ACLs, and
   verify-at-use?
9. Are new dependencies locked and audited?
10. Is a changelog entry present for any user-visible security change?
